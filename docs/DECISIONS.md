# Implementation decisions

## M1 Foundation

- **DEC-001 — Mongo health behavior:** `/api/health` always responds with process health and reports MongoDB connection state separately. This keeps the endpoint useful while a local database is starting.
- **DEC-002 — Frontend theme:** The initial shell uses a responsive dark case-file theme that can be extended during later gameplay milestones.
- **DEC-003 — Milestone scope:** Work follows `spec.md` Section 20; later milestone features are intentionally not scaffolded as functional flows before earlier acceptance criteria are met.
- **DEC-004 — Optional object storage:** M4 implements the storage interface and local driver. S3 remains optional and deferred; configuring `STORAGE_DRIVER=s3` fails clearly until its driver is added.

## Phase A — Hygiene & foundation gaps (2026-11-14)

- **DEC-005 — Leaked credentials:** The original `server/.env.example` contained a live MongoDB Atlas connection string. It was replaced with a local placeholder. The Atlas user password must be rotated by the account owner; the old value remains in public git history and must never be reused.
- **DEC-006 — Mongo query sanitisation:** `express-mongo-sanitize` is incompatible with Express 5 (it reassigns the read-only `req.query`). Instead, `middleware/security.ts#rejectMongoOperators` rejects any body key starting with `$` or containing `.`, all bodies are parsed by strict Zod schemas, and route params are validated (e.g. `CaseIdSchema`). Mongoose's global `sanitizeFilter` was **not** enabled because it would neutralise the server's own `$in`/`$gte`/`$exists` filters.
- **DEC-007 — Rate-limit buckets:** Spec §15.4 sets a global limit of 100 requests / 15 min / IP, but status polling every 2 s (§4) alone needs ~450 / 15 min. `GET /api/cases/:id/status` and `GET /api/media/*` therefore use a separate polling bucket (default 1000 / 15 min). Auth endpoints (register, login, guest, upgrade) share a stricter bucket (20 / 15 min); case creation has a per-IP cap (20 / hour) on top of FR-06 per-user limits. All limits are env-configurable and return the standard `RATE_LIMITED` error body.
- **DEC-008 — API port 5050 and Vite proxy:** macOS reserves port 5000 for AirPlay Receiver, so the spec's default `PORT=5000` silently fails on Macs. The API defaults to **5050**. In development the client calls same-origin `/api` and Vite proxies it to the API, so session cookies are first-party and no CORS preflight is needed. `VITE_API_BASE_URL` still overrides this for split-origin deployments, and CORS remains restricted to `CLIENT_ORIGIN`.
- **DEC-009 — `GET /api/auth/me` when signed out:** Returns `200 { "user": null }` instead of `401`, so anonymous visitors on public pages do not produce failed-request console errors. A tampered or expired cookie is treated as signed out and cleared. All other protected routes still return `401 UNAUTHENTICATED`.
- **DEC-010 — Database unavailability:** Mongoose `bufferTimeoutMS` is 3 s (fail fast instead of 10 s hangs). The server keeps retrying the initial connection with backoff, and database errors map to HTTP 503 with code `INTERNAL` (the spec's error code list has no dedicated code).
- **DEC-011 — Malformed bodies:** Invalid JSON returns `400 VALIDATION_ERROR`; bodies over 100 kB return `413 VALIDATION_ERROR`.
- **DEC-012 — Logging:** pino + pino-http with a request ID per request (`X-Request-Id`, accepted from the caller if well-formed). Cookies, authorization headers, passwords and API keys are redacted; request bodies are never logged. Logs are silent under `NODE_ENV=test`.
- **DEC-013 — Default Gemini model names:** Defaults reset to the spec §17 suggestions (`gemini-2.5-flash`, `gemini-2.5-flash-image`). They must be verified against Google's current model list in Phase B before real generation is accepted.
- **DEC-014 — Playwright installed early:** The spec's E2E smoke test (§18) was added in Phase A to verify the UI in a real browser after each phase. It runs desktop and mobile (Pixel 7) projects against mock Gemini.

## Phase B — Real Gemini integration (2026-11-14)

Findings from a real free-tier key: `gemini-2.5-flash` (the spec's suggested default) is closed to new users; `gemini-3.8-flash` exists but was overloaded (503/504); `gemini-3.5-flash` works but takes 20-30 s per call on the free tier; `gemini-3.5-flash-lite` answers in about 2 s; every image model allows **0 requests per day** on the free tier.

- **DEC-013 (revised):** The original default names (`gemini-3.8-flash`, `gemini-nano-banana-2.1`) were valid; the audit was wrong to call them suspect. New defaults are chosen for availability: `GEMINI_TEXT_MODEL` and `GEMINI_VALIDATOR_MODEL` = `gemini-3.5-flash`, `GEMINI_IMAGE_MODEL` = `gemini-nano-banana-2.1`.
- **DEC-015 — Image generation is opt-in:** `ENABLE_IMAGE_GENERATION=false` by default. When off, Stage 3 is skipped: portraits, photo evidence and CCTV frames use styled placeholders (`mediaStatus: "placeholder"`) and keep their AI-written caption, alt text, frame notes and log. The blind validator already works from that text (spec §9 Stage 4), so solvability is unaffected. The >30% media-failure rule applies only when images are enabled. Turning it on requires a billing-enabled key.
- **DEC-016 — Evidence generated in batches:** Spec §9 Stage 2 suggests one call per item. Evidence is instead generated in batches of up to 5 items per call (concurrency 3), and every batch sees the full hidden plan (truth, timeline, secrets, whole clue map). This cuts a medium case from ~11 evidence calls to 3 and keeps times, places and names consistent across items (fairness rule 5). Each clue plan entry now carries an `evidenceType`, so the FR-11 type mix is checked on the blueprint before any evidence is written, and each batch must return exactly the planned types.
- **DEC-017 — Model routing and fallback:** `GEMINI_TEXT_MODEL` writes the blueprint and `GEMINI_VALIDATOR_MODEL` runs the blind check (quality matters most). `GEMINI_FAST_MODEL` writes evidence and screens seeds. If a call fails with 5xx, a gateway deadline or our own timeout, it is retried once on `GEMINI_FALLBACK_MODEL`. Text timeout is `GEMINI_TEXT_TIMEOUT_MS` (default 120 s) instead of the spec's 60 s, because free-tier latency alone can reach 30 s.
- **DEC-018 — Case-local timestamps:** Models chose different UTC offsets per batch while writing consistent clock times. All evidence timestamps are now case-local wall-clock times stored with a `+00:00` suffix: the prompt asks for this and the server rewrites any other offset, keeping the clock time. The client must display them with `timeZone: 'UTC'` so 21:41 in the story shows as 21:41 everywhere.
- **DEC-019 — No automatic retry on 429:** NFR-03 asks for retries on 429. Gemini 429s on the free tier are daily quota exhaustion, so retrying only burns time; the case fails with `AI_QUOTA_EXCEEDED` and a `retryAt` when Google provides one. 5xx and network errors are still retried with backoff.
- **DEC-020 — Evidence-stage retries keep the blueprint:** If only the evidence fails validation, the next attempt reuses the blueprint (spec FR-13 allows regenerating from Stage 2). A blind-validator failure regenerates from Stage 1, since the plan itself may be unsolvable.
- **DEC-021 — Regenerate endpoint (API-13):** `POST /api/cases/:id/regenerate` re-queues only `failed` cases owned by the caller. It refuses content-policy failures (422), waits for a quota `retryAt` (429), respects the 2-concurrent limit, and uses a conditional update so double-clicks cannot enqueue twice. Retries do not count against the daily creation limit but share the per-IP generation limiter.
- **DEC-022 — Fallback on daily quota:** On the free tier `gemini-3.5-flash` allows 20 requests per day (about 8-10 cases, since each case uses it twice). When a model's daily quota is exhausted, the call is retried on `GEMINI_FALLBACK_MODEL` instead of failing the case; the blind validator still gates solvability. Short per-minute limits are waited out (up to 3 times) and a process-wide pacer caps simultaneous Gemini calls (`GEMINI_MAX_CONCURRENT_CALLS`, default 3). The regenerate endpoint only blocks for a short (≤ 5 min) recorded wait, because a far-off daily reset may be served by the fallback model.
